# 一箭又一箭（Yet Arrow Away）

一个用 Python + Pygame 写的益智小游戏：点击棋盘上的箭头，让它沿着自己指的方向飞出棋盘；前方有别的箭头挡路就飞不出去，还会扣掉一次机会。把所有箭头清空即可过关。

## 游戏简介

棋盘上散布着朝**上、下、左、右**四个方向的箭头。

点中一个箭头后，程序会沿它指的方向一路检查到棋盘边界：

- **路上一个箭头都没有** —— 该箭头飞出棋盘并被消除；
- **路上碰到别的箭头** —— 该箭头不能消除，扣一次失误机会，并晃动变红提示。

清空当前关卡的全部箭头即通关；失误次数耗尽则本关失败，可以重新开始。

游戏共 **3 个关卡**，难度递进，每关都有倒计时：

| 关卡 | 棋盘 | 箭头数 | 爱心 | 时间限制 | 时间道具 | 开局可飞 |
| --- | --- | --- | --- | --- | --- | --- |
| 第 1 关 · 牛刀小试 | 6 × 6 | 9 | 2 | 10 秒 | 1 个（+5 秒） | 4 个 |
| 第 2 关 · 渐入佳境 | 7 × 7 | 14 | 2 | 15 秒 | 1 个（+5 秒） | 4 个 |
| 第 3 关 · 步步为营 | 8 × 8 | 20 | 2 | 20 秒 | 1 个（+5 秒） | 5 个 |

### 时间限制

每关都有一个倒计时，显示在右上角的进度条上（颜色随时间从绿变黄再变红，最后 10 秒会闪烁）。

**时间归零仍未清空棋盘，同样判定本关失败**，界面标题会显示「时间到！」并提示还剩几个箭头。

时间给得很紧（10 / 15 / 20 秒），是有意设计的压力：必须先把「哪几个箭头前方是空的」扫一遍再动手，
而不是点一下想一下。

### 爱心（剩余机会）

界面左上角用一排爱心表示剩余机会：**亮红实心**是还剩的，**暗色空心**是已经失去的。
点错一次灭一颗，心形的绘制见下方「实现思路」。

每关统一给 **2 颗**爱心。这个数字是有讲究的：给 3 颗以上容错太足，玩家可以乱点碰运气；
只给 1 颗又太苛刻，一次手滑就要重来。2 颗刚好是「允许犯点小错，但不能一直瞎试」的平衡点。

### 时间道具（不能点，要靠箭头飞过）

棋盘上放着一个发光的表盘图标，**点它是没用的**——
只有当某个箭头沿着自己的方向飞出棋盘、飞行路线正好穿过道具所在的格子时，才会把它带走。

这样一来，道具从「顺手一点的按钮」变成了**路线规划的副产品**：你得把某个箭头留到正确的时机，
让它从道具上面穿过去。每关只放**一个**，而且只加 **5 秒** ——
在 10 秒的关卡里这等于多了一半时间，是货真价实的救命稻草。

三个关卡的道具位置都是挑过的，吃法都要求「先清掉挡路的箭头，再让后手飞过去」：

| 关卡 | 道具位置 | 怎么吃到 |
| --- | --- | --- |
| 第 1 关 | (1,3) | 先点掉 (1,2) 的 `U`，(1,0) 的 `R` 才能一飞到底扫过它 |
| 第 2 关 | (3,6) | 走完 (2,0)`L` → (2,6)`L` → (4,6)`U` 这条链，才轮到 `R` |
| 第 3 关 | (3,3) | 先清掉 (4,1)`L` 和 (4,3)`L`，(2,3) 的 `D` 才能一路向下扫过它 |

「道具一定吃得到」和「开局不能白送」这两条性质都由自动测试守着 ——
万一以后调关卡把道具挪到了谁都扫不到的死角，测试会立刻报错。

### 结算表情图

过关 / 失败 / 全部通关时会弹出一张表情图（带「弹一下」的入场动画）。
图片放在 `resources/` 目录，缺失时程序会自动跳过绘制，不会崩。

## 游戏操作说明（规则详解）

1. 每个箭头只能沿**自己指的方向**移动，而且是直接飞出棋盘，不会停在半路。
2. 判断标准是「箭头与棋盘边界之间还有没有别的箭头」——只看**同一行或同一列**。
3. 箭头贴着棋盘边缘、且朝着棋盘外时，可以直接飞出（这是最容易写错的地方）。
4. 点错一次熄灭一颗爱心，爱心全灭本关失败。**点错不会改变棋盘**，可以放心试探。
5. **每关都有倒计时，时间归零还没清空同样失败。**
6. 棋盘上发光的表盘是**时间道具**：点它没有反应，
   必须让某个箭头飞出时从它所在的格子穿过去，才能 +5 秒。
7. 每一关都可以重新开始，棋盘布局、爱心数量、倒计时和道具会**全部**恢复到初始状态。

### 为什么把逻辑层和界面层分开

`arrows.py`、`levels.py`、`solver.py` **完全不依赖 pygame**，好处有两点：

1. **测试方便** —— 路径判断、关卡可解性都能写成自动测试，不用手点鼠标；
2. **职责清晰** —— 界面层不重复实现任何游戏规则，所有判定都调用逻辑层。

## 实现思路

### 1. 箭头和方向怎么表示

方向用四个字符常量表示（`U`/`D`/`L`/`R`），每个方向对应一组「行增量、列增量」：

```python
DELTA = {
    "U": (-1, 0),   # 行索引向下增长，所以「上」是 -1
    "D": (1, 0),
    "L": (0, -1),
    "R": (0, 1),
}
```

棋盘用字典存储箭头：键是格子坐标 `(行, 列)`，值是方向。**不存空格子**，所以「某个位置有没有箭头」就是判断这个键在不在字典里，查询很快。

### 2. 路径检测（本程序的核心）

从箭头**下一个格子**开始，沿它指的方向一格一格往外走：

```python
dr, dc = DELTA[direction]
nr, nc = r + dr, c + dc

while self.in_bounds(nr, nc):        # 只要还在棋盘内就继续走
    if self.has_arrow(nr, nc):       # 碰到箭头 -> 被挡住
        return False, (nr, nc)
    nr += dr
    nc += dc

return True, None                    # 走出棋盘了 -> 可以飞出
```

**这段代码最关键的地方在于「越界」和「被挡住」必须分开处理。**

朝棋盘外的箭头，索引会算到 `-1` 或者超出列数。如果写成「先访问再判断」就很容易抛 `IndexError`。
这里把 `in_bounds()` 作为循环条件，索引一旦越界循环就自然结束，直接返回「可以飞出」——
从结构上避免了越界访问，不需要任何特判。

### 3. 飞行路线：道具怎么吃到

除了「能不能飞出去」，还需要知道一个箭头**会经过哪些格子** —— 这是时间道具的判定依据。
它和路径检测共用同一套走法，只是不检查有没有被挡住，而是一路把经过的格子收进列表：

```python
def path_cells(self, r, c):
    direction = self.arrows[(r, c)]
    dr, dc = DELTA[direction]
    nr, nc = r + dr, c + dc
    cells = []
    while self.in_bounds(nr, nc):     # 走到边界就停，和上面一套思路
        cells.append((nr, nc))
        nr += dr
        nc += dc
    return cells
```

**这里有个顺序陷阱：必须在箭头从棋盘移除之前调用它。**
`path_cells` 的第一步是确认这个格子有箭头，箭头一旦 `remove` 掉，方法直接返回空列表，
这一趟的飞行路线就彻底查不到了 —— 结果就是道具永远吃不到。
所以游戏里的顺序固定为「先收集路线上的道具 → 再移除箭头 → 最后播飞出动画」：

```python
got = self._collect_events_on_path(r, c)   # 先算路线，此时箭头还在
self.board.remove(r, c)                    # 再移除
self.flying.append({...})                  # 最后才是视觉动画
```

这条约束容易被后来改动破坏（看起来两个操作换个位置没差别），所以专门写了一个
「箭头移除后飞行路线变空」的测试把它锁住。

### 4. 关卡怎么表示

关卡用字符网格写，直观好改：

```python
"grid": [
    ". D . D . . .",
    ". . . . . . .",
    ". D . D . . .",
    "R R R R R R .",
    ...
]
```

`.` 是空格子，`U`/`D`/`L`/`R` 是四个方向的箭头。

### 6. 爱心怎么画出来的

剩余机会用爱心表示，比数字直观。爱心是用**参数方程**算出来的，不依赖字体里有没有「♥」字符：

```
x = 16·sin³t
y = 13·cos t − 5·cos 2t − 2·cos 3t − cos 4t
```

采样 60 个点连成多边形，再把坐标归一化到统一范围，这样换任何尺寸都不用改数字。
一组爱心画出来后，还剩的填亮红色，已经失去的只画暗色轮廓 —— 一眼就能看出还剩几条命。

### 7. 关卡怎么设计的（含两个坑）

关卡不是手工摆的，而是由 `level_gen.py` 生成、再按条件筛选。生成需要同时满足：

1. 四个方向都必须出现，避免玩法单调；
2. **同一行或同一列上，相邻位置连续同方向的箭头不能超过 2 个**；
3. 开局能直接飞走的箭头不能太多；
4. 必须能被 `solver.py` 验证确实可以通关。

**坑一：面对面死锁导致整关无解。**

同一行或同一列上，不能出现两个箭头「面对面」互相指着对方。例如一行写成 `R . . . L`：

- 左边的 `R` 想往右飞，被右边的 `L` 挡住；
- 右边的 `L` 想往左飞，被左边的 `R` 挡住。

两个箭头谁都动不了，整关直接**无解**。这个错误肉眼看不出来（第一版第 2 关就是这么写坏的），
所以后来规定：**每个关卡生成完都必须跑一遍求解器**。

**坑二：过度追求「有序」，做成了「机械」。**

为了压住通关路径数量，早期版本用「一整排同方向箭头」当主链 —— 它们首尾相接，
只能从最外侧开始逐个清理，顺序确实唯一了。但代价是：玩家只要从最右边一路点过去就行，
**完全没有思考和判断**，试玩反馈是「显得很呆」。

修正办法是把「顺序唯一」换成「方向交错」：限制同一行/列上相邻连续同方向的箭头不超过 2 个。
现在每一关的方向都是混着来的，每点一步都要重新看哪个箭头还有出路。

**顺带纠正一个认知：难度不能看通关路径数。**

这个游戏里「移除箭头只会让路更通，不会新增阻挡」，所以玩家**不可能点错顺序把局面点死** ——
任何当前能飞的箭头，点了都是安全的。于是通关路径数动辄几千条，但这个数字大并不代表简单。
真正的难度来自：**箭头总数**（要观察的信息量）和**开局可飞箭头数**（下手难度），
以及后期加上的**倒计时压力**。

### 8. 求解器怎么工作

求解器用的是**深度优先搜索 + 记忆化**：

- 每一轮先找出当前所有「可以飞出去」的箭头；
- 任选一个让它飞出，局面就少一个箭头；
- 在新局面上重复这个过程，直到清空（成功）或者一个能飞的都没有（死局，退回换一种点法）。

同样的局面会被反复遇到，所以用一个字典把算过的局面记下来，避免重复搜索。

求解器有两个用途：**验证关卡可解**，以及给游戏提供**提示功能**
（提示时逐个试，只推荐「点了之后仍然可解」的安全走法，避免把玩家带进死路）。

### 测试过程中发现并修掉的问题

1. **第 2 关原本无法通关** —— 关卡里出现了「面对面互相挡死」的两个箭头。
   是求解器查出来的，改掉那个箭头方向后恢复正常。
2. **游戏启动后直接进第 1 关，开始界面不显示** —— 初始化时误把状态设成了「游戏中」。
   是流程测试查出来的。
3. **顶部信息栏文字重叠** —— 关卡名太长，和右边的数据挤在一起。
   看导出的截图时发现，改成关卡名单独占一行。
4. **操作反馈文字和结算文字重叠** —— 调整了反馈文字的位置和绘制顺序。
5. **棋盘没有水平居中** —— 计算棋盘宽度时，把「格子间距」也按格子数量算了，
   但实际间距比格子数量少一个。改成 `列数 * 边长 + (列数 - 1) * 间距` 后居中正常。
6. **事件道具可以重复点击、无限刷奖励** —— 发奖励时没有先判断是否已触发。
   虽然调用方会过滤已触发的道具，但发奖励属于有副作用的操作，自己也应该有防护。
   已加上守卫，并补了对应的测试。
7. **结算表情图顶出窗口外** —— 图片纵向位置写死了，换成大图就被裁掉。
   改成按图片实际高度计算整块内容的位置，整体在窗口里居中。
8. **搬动道具时差点让飞行路线算不出来** —— 「箭头飞过才算拿到」需要在箭头
   从棋盘上移除**之前**查它的飞行路线，一旦顺序写反，`path_cells` 会直接返回空列表，
   道具永远吃不到。已在代码里写明这个顺序约束，并加了「移除后路线变空」的测试锁住它。

## 玩法参数的调整过程

这部分是试玩之后几轮调整的记录，也是设计思路的一部分。

| 轮次 | 反馈 | 改动 |
| --- | --- | --- |
| 初版 | 棋盘太小、箭头太少 | 棋盘放大到 6×6 / 7×7 / 8×8，箭头增至 9 / 14 / 20 |
| 第二轮 | 第 2、3 关有同方向箭头聚成一排，连续点掉「显得很呆」 | 增加约束：同一行/列连续同方向箭头不超过 2 个，并写成测试防回归 |
| 第三轮 | 需要严格的倒计时，失败/成功要弹出表情图 | 加入倒计时条（最后 10 秒闪烁）、结算表情图（带弹入动画） |
| 第四轮 | 「剩余机会：n」不够直观 | 改成爱心：亮红实心表示还剩，暗色空心表示已失去 |
| 第五轮 | **时间给太多、爱心给太多、道具太容易拿** | 时限收紧到 10 / 15 / 20 秒；爱心统一 2 颗；道具从「点击获取」改为「箭头飞过才能获取」，每关只留 1 个 +5 秒的 |

第五轮的三条改动其实是同一个目的：**把「随便点都能过」变成「必须规划」**。
时间紧 → 不能慢慢试；爱心少 → 不能靠试错找答案；道具要靠飞过才拿到 → 必须提前想好哪个箭头什么时候放。
三条加在一起，游戏才真正开始要求玩家「看一眼棋盘，在脑子里排个序」。

## 素材来源

## 已知问题

- 在 Python 3.13 环境下，pygame 的 `font.SysFont()` 和 `font.get_fonts()` 会抛出
  `TypeError: expected str, bytes or os.PathLike object, not int`。
  本项目因此改为用**字体文件路径**直接加载
  （按「微软雅黑 → 黑体 → 宋体 → 等线」的顺序尝试，全都没有才退回默认字体），
  不依赖 `SysFont`，已实测可正常渲染中文。
- 游戏窗口尺寸固定为 880 × 800，暂不支持调整大小。
- **打包成 exe 分发时**：如果对方的电脑缺少 Visual C++ 运行库，
  程序可能无法启动。这个没法在开发机上预先验证，出问题时安装一次
  VC++ Redistributable（2015-2022）即可。
- 打包后若出现异常，程序会在 exe 同目录生成 `错误日志.txt`，方便定位问题
  （`--windowed` 模式没有控制台，不写日志就完全看不到报错）。

## 打包成 exe 分享给别人

游戏可以打包成一个**无需安装任何东西、双击即玩**的 exe。

- 双击 `build_exe.bat` 一键完成打包（含图标生成、打包、自检、压缩）。
- 产物：`dist/yet-arrow-away.exe`（约 14 MB）和 `yet-arrow-away_免安装版.zip`。

打包过程中解决的几个关键问题（详见 [`打包说明.md`](打包说明.md)）：

| 问题 | 原因 | 解决 |
| --- | --- | --- |
| 打出来 176 MB，微信发不出去 | Anaconda 的 numpy 连带 Intel MKL 被打进包，光 DLL 就几十 MB，而本项目根本不用 numpy | 用 `--exclude-module` 排除 numpy / mkl / psutil / setuptools 等，降到 **14.3 MB** |
| 打包后找不到表情图 | 单文件 exe 运行时会解压到临时目录，`__file__` 指向那里而不是 exe 所在目录 | 统一用 `app_path()`，打包态取 `sys._MEIPASS`；打包时用 `--add-data` 捎上资源 |
| 换台电脑中文可能变方块 | 字体路径写死了微软雅黑，别人机器上不一定有 | 改为按候选字体列表依次尝试 |
| 打包后闪退看不到报错 | `--windowed` 没有控制台 | 异常写入 exe 旁的 `错误日志.txt` |
| 资源/字体问题在自己机器上测不出来 | 源码目录下一切正常 | 给游戏加了 `--smoke` 自检模式：用虚拟显示驱动渲染各界面存图，并检查表情图和字体，打包脚本会自动跑一遍 |
